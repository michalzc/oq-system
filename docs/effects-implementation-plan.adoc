= Active Effects — implementation plan
:icons: font
:toc: right

Roadmap item: v0.9, https://github.com/michalzc/oq-system/issues/14[#14]
(README.md:20-27). Branch: `feature/#14-active-effects-support`. Line
references are to commit `e161fdb`; recheck them after each task.

== Goal

Make Active Effects work for OpenQuest values. Effects use a small,
system-owned vocabulary of *keys*, not data paths. The system applies
each key at the right step of data preparation, so: - a STR effect
changes the damage modifier; - a CON effect changes HP max; - a skill
effect changes every weapon and spell that uses the skill.

Effects never change stored fields, so their values are never saved into
sheet or dialog forms.

Today effects are inert. `OQBaseActor.prepareEmbeddedDocuments`
(`src/module/document/actor/base-actor.js:67-77`) calls
`applyActiveEffects('initial')` after characteristics, HP, MP, DM, MR
and every skill, weapon and spell value have been calculated. Only `ap`
and `initiative`, which are calculated later, could react to an effect.

== Decisions

* *HP/MP:* an effect that raises `attributes.hp` or `attributes.mp`
raises max and current by the same amount.
** When the effect’s contribution goes down (the effect ends, is
disabled or suppressed, or is negative), current is only capped at the
new max.
** This matches Vigour: ``damage comes off the magical hit points
first'' (SRD Personal Magic 970-974).
** Characteristic effects (CON, SIZ, POW) change max only. This matches
Enhance (POW), which ``does not increase the character’s magic points''
(SRD Sorcery 587).
** Accepted side effect: removing a negative HP effect from a wounded
character gives the HP back.
* *Skills:* `skills.<slug>` changes the skill *value*.
** Bonuses stack, and flow into weapons, spells and the initiative
declaration.
** The skill’s `mod` and the roll dialog’s ``Other mods'' stay for
situational modifiers.
* *Damage modifier:* the base stays the STR+SIZ table plus `dm.mod`, so
STR/SIZ effects move along the table. An `attributes.dm` effect is a
formula term: `add` appends it (`+1d6`, `+1`), `override` replaces the
whole value.
* *Extra keys from the spell survey:*
** skill groups;
** skills by base characteristic;
** armour item AP;
** a weapon damage dice multiplier.

The numeric change types are `add`, `subtract`, `multiply`, `override`,
`upgrade` and `downgrade`.

* *Order:* changes apply in priority order: `change.priority`, or else
the type’s default (multiply 10, add/subtract 20, downgrade 30, upgrade
40, override 50). Ties keep insertion order.
* *Rounding:* numeric results are rounded up once per chain, as the SRD
rounds up.
* *Not targetable:* `attributes.gr` (growth points) and `attributes.fn`
(fortune points).
* *Ignored keys:* any other key, `system.*` included, does nothing and
is flagged in the effect sheet.
* *Not supported in values:* `@` references.
* *Transfer:*
** Actor keys on an item’s effect apply only when `transfer` is on (core
rule).
** `item.*` keys apply to the item holding the effect, whatever
`transfer` is set to.
* *Phase:* the change `phase` is ignored for system keys.
* *Slugs:* slugs come from skill names (`makeSlug`,
`src/module/utils/utils.js:26`).
** The SRD skill is Close Combat (`close-combat`); there is no Melee
Combat.
** Renaming a skill breaks effects that use its slug, as it already does
for weapons and spells.
* *Suppression:* an item’s effects are suppressed in these cases:
** spells: always — their effects are templates, and a known spell is
not an active spell;
** armour: unless worn or natural;
** weapons and equipment: while stored;
** skills and special abilities: never.

== Foundry v14 facts the tasks rely on

All of these were checked in the Foundry 14.368 sources
(`foundryvtt-api/`).

* *Preparation order:* `system.prepareBaseData` →
`actor.prepareBaseData` → `prepareEmbeddedDocuments` →
`system.prepareDerivedData` → `prepareDerivedData` →
`applyActiveEffects('final')`
(`client/documents/abstract/client-document.mjs:313-320`,
`client/documents/actor.mjs:428-446`).
** When `actor.prepareBaseData` runs, items and effects are initialised
from source but not yet prepared in this cycle
(`client-document.mjs:60-67`).
* *Change data:* `effect.system.changes[]` holds
`{key, type, value (AnyField), phase ('initial'), priority   (nullable)}`
(`common/data/active-effect.mjs:15-25`).
** Default priorities are in `CONST.ACTIVE_EFFECT_CHANGE_TYPES`
(`common/constants.mjs:107-160`).
** `ActiveEffect#prepareBaseData` fills in `priority`
(`client/documents/active-effect.mjs:265-272`).
** `custom` is a core type and appears in the type dropdown.
* *Where changes are applied:* `Actor#applyActiveEffects(phase)`
(`actor.mjs:212-272`) applies only the changes for which
`effect.shouldApplyChange(change, {phase})` returns true (l.245).
** Statuses are collected per effect regardless (l.254-256).
** `token.*` changes are routed to tokens (l.248-252).
** Any other key goes to `_applyChangeUnguided`
(`active-effect.mjs:594-674`). For `characteristics.str` that merges a
garbage property onto the actor, so `shouldApplyChange` must reject
system keys.
* *Suppression:* `isSuppressed` is
`!!(this.system.isSuppressed ?? this.duration.expired)`, and `active` is
`!disabled && !isSuppressed` (`active-effect.mjs:191-211`).
* *Which effects reach the actor:* `Actor#allApplicableEffects` yields
actor effects plus item effects with `transfer` (`actor.mjs:305-314`).
Core never applies effects to items.
* *Effect config sheet:* `ActiveEffectConfig` JSON-parses change values
on submit
(`client/applications/sheets/active-effect-config.mjs:202-207`). `"10"`
becomes 10; `"+5"` and `"1d6"` stay strings. The `phase` field is a
hidden input (`templates/sheets/active-effect/change.hbs`).
* *Descendant events:* the client backend runs `preX` → `parent.reset()`
→ `onX` with no `await` in between (`client/data/client-backend.mjs`:
create l.155/168/173, update l.319/342/348, delete l.447/471/477).
** For an item’s effects, core
`Actor._on{Create,Update,Delete}DescendantDocuments` resets the actor
(`actor.mjs:712/730/748`), so system code must run after `super`.
** `ActorDelta` replays the events on its synthetic actor
(`client/documents/actor-delta.mjs:241-248`, reset l.115-119).
* *Expiry:* `ActiveEffectRegistry.refresh` marks expired effects
(`duration.expired: true`) only on the active GM’s client
(`client/helpers/active-effect-registry.mjs:146-166`). The default
`CONFIG.ActiveEffect.expiryAction` is `"update"`, so expired effects
stay on the document.
* *Drag and drop:* `ActorSheetV2` and `ItemSheetV2` already drag
`.draggable` rows with `data-effect-id` (and `data-item-id`), and create
dropped effects
(`client/applications/sheets/actor-sheet.mjs:224-238, 308-314`,
`item-sheet.mjs:100, 168`).
** Core refuses to drop an effect from an actor’s own item onto that
actor (`actor-sheet.mjs:311`).
* *Compendium effects:* they are created with `transfer: false`
(`common/documents/active-effect.mjs:126-129`). `ActiveEffect` is a
primary document type only in compendiums; there is no world sidebar for
effects.
* *Sheet registration:* use
`foundry.applications.apps.DocumentSheetConfig.registerSheet(cls, scope, sheet, opts)`
(`client/applications/apps/document-sheet-config.mjs:410-424`). Don’t
write `CONFIG.*.sheetClasses` directly.
* *Possible core bug:* `Item._preCreate`
(`client/documents/item.mjs:91`) passes the effect start without a
`{start}` wrapper. Timed effects on items may then never get `start` and
never expire (`isExpiryTrackable`, `active-effect.mjs:233`). Timed buffs
belong on the actor; check this in the game.

== Conventions for every task

* *Before ticking a task:* run `yarn test` and `yarn lint`. Tick the
checkbox and add a short *Resolution* note under the task.
* *`src/module/utils/effects.js` stays pure and importable by mocha:*
** no `foundry`, `CONFIG` or `game` at module evaluation;
** no imports from `consts/*`, because `items-config.js` imports sheets;
** lodash is fine;
** keep local constants with ``keep in sync with …'' comments.
* *Prepared state on documents:* use plain properties assigned during
preparation (`this.oqEffectChanges`).
** Never `#private` fields or class field initialisers. Preparation runs
inside the constructor; core uses `overrides = this.overrides ?? {}` for
the same reason.
* *Effects only change prepared values.* Forms bind stored fields, read
from `_source` where prepared and stored values can differ.
* *Document tests:* follow the stubbed-globals pattern of
`test/test-spell-casting.js` and `test/test-combat.js`. Save and restore
the globals; stub `Actor`, `Item`, `ActiveEffect`, `Roll` and
`CONFIG.OQ`; import dynamically after stubbing; polyfill
`String.prototype.slugify` for `makeSlug`.
* *Labels:* go under `OQ.Effects.*` in `src/lang/en.yaml`.
`OQ.Nav.Effects` already exists (`en.yaml:270`).
* *Styles:* go in a new `src/styles/sheet/effects.less`, imported where
the other sheet styles are.

== Risks and notes

* *`getRollData` / `getDataForItems`:* they expose effect-modified
values (`@str`, `@skills.x.value`, `@dm`). This affects macros, and the
magnitude set when a sorcery spell is created (`spell.js:23-28`), which
uses the casting skill.
* *Performance:* one pass over the applicable effects per preparation,
plus small per-skill merges. There is a fast path for actors without
effects.
* *Duplicate skill names:* both skills receive a `skills.<slug>` change.
A renamed skill silently stops matching; the config sheet warns about
unknown slugs.
* *Change types:* `custom` and module change types are ignored on system
keys and flagged in the sheet.
* *Future work:* temporary HP/MP above max (#124) must work alongside
`effectMod`. Keep the rule in `adjustResourceValue`.

== Out of scope (follow-ups from the spell survey)

* Status conditions (#109): prone, blinded, unconscious, demoralised,
fatigued, berserk, befuddled, shaken, …
* Temporary HP/MP above max (#124, Tap) and magic point stores (#96).
* Applying spell effects when a spell is cast, magnitude scaling, and
`@` references in values.
* The SRD rule that ``only the most powerful magic modifier applies''
(SK:276-284), and spell exclusivity groups. The GM disables overlapping
effects.
* Conditional and one-shot modifiers: against mind magic, against an
element, ``next test only''.
* Damage type, magical damage, armour penetration, immunities,
spell-blocking magnitudes, extra attacks.
* An effects compendium for the SRD spells.
